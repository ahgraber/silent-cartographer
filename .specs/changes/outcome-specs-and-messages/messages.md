# User-facing message audit

Read-only audit of every message a user or agent reads when something is wrong, degraded, refused, or needs action.
Scope: Rust CLI in `src/`, Python MCP server in `mcp/src/c10r_mcp/`, on branch `main`.
Excluded: `evals/`, tests, debug logs, and purely informational success output.
The `cargo metadata` warning quoted in the brief is not in the code yet.
Today the only trace of that failure is `library_roots` in `src/semantic/rust_adapter.rs:100-110`, which silently returns an empty map on a spawn failure, a non-zero exit, or a timeout.

Grades are written W/C/I/R (what happened, cause, implication, remedy).
`ok` = present, `miss` = missing, `n/a` = cannot apply or self-explanatory.
`Meets` is `Y` when every applicable criterion is ok, `Y*` when it is a trivially self-explanatory usage error that needs less than four criteria, and `N` otherwise.

## 1. Summary

- Message rows graded: 122 (rows in section 2, counted per distinct template or tightly related group; a few rows group several near-identical strings).
- Meeting the standard: 63 (42 fully `Y`, 21 `Y*` trivially self-explanatory).
- Not meeting it: 59, of which 10 are marked low priority.
- Rows C13, C14, C32, and P-16 are cross-references or pass-through and are not counted.
- Pass-through wrappers that carry another message unchanged (`Failure::Usage(String)` and friends in `src/exit.rs`, `errors.failure` in the MCP server, the `UsageErrors` middleware) are not counted.
  They are graded through the messages they carry.

### Five most impactful gaps

1. **Indexer setup failures on a first `build`** (`src/commands.rs:541`, `src/semantic/rust_adapter.rs:39-47`, `src/semantic/python_adapter.rs:84-98`).
   - A missing `rust-analyzer` prints `rust-analyzer unavailable: semantic backend unavailable: cannot run rust-analyzer: No such file or directory (os error 2)`.
   - It states the cause but gives no install command, though `doctor` already knows `rustup component add rust-analyzer`, and no mention of the `--rust-analyzer` flag.
   - A tool that is present but silent for 10 s is also labeled `unavailable`.
   - `--version failed` drops the exit status and stderr that the code holds in `capture`.
   - For Python, `scip-python ... --version failed; install scip-python with ...` advises installing a tool that is already installed.
   - `rust-analyzer scip exited with status N` and `scip-python index exited with status N` do not say that the tool's own error output was written to the terminal just above them.
2. **Staleness labels** (`src/render.rs:845-847`, `src/commands.rs:~318-340`).
   - `stale (content changed)`, `stale (analyzer version changed)`, `stale (environment changed)` say what differs but not what it means for the answer (it may describe code that no longer exists).
   - `stale (environment changed)` is also produced when the environment merely could not be resolved or its interpreter timed out.
   - The code deliberately treats an unresolvable environment as absent, and the freshness comparison then reports drift.
   - The label therefore states a cause (changed) that is not what happened.
3. **Workspace relation warnings** (`src/render.rs:637-641`).
   - `warning: whether this index describes this workspace could not be determined` has no cause, implication, or remedy.
   - `warning: this index describes a different workspace (built for X)` has no implication or remedy.
   - The status report line `workspace relation: unknown` is terser still.
4. **Store newer than the binary** (`src/graph/store.rs:660-664`).
   - `SchemaVersionMismatch` always advises `run c10r build to rebuild it (or delete the file)`.
   - When `found > expected`, a different, newer c10r wrote the store, and the right action is to upgrade c10r or point `--db` elsewhere.
   - Rebuilding would replace the newer store, which breaks the other build that shares it (`CLAUDE.md` notes the installed and working-tree builds share `.c10r/index.db` by default).
   - Both numbers are in scope, so the message can branch on them.
5. **Git boundary messages** (`src/git.rs:27-45`).
   - `git could not be run (...); `impact`requires a working`git` to seed a diff` is printed by `hooks install`, `hooks uninstall`, `hooks run`, and `doctor` too, where the `impact` clause is wrong.
   - `{0} is not inside a git worktree` prints `.` when the root is the current directory.
   - `did not complete within the 10-second bounded deadline` uses internal jargon, and none of the git messages say what the user should do or that no answer was produced.
   - `hooks run` failures (`src/commands.rs:3044-3050`) say that a refresh failed but not that the index is now stale or what to run.

Other gaps worth noting:

- `QueryError` corruption messages say `rebuild the index`, but plain `c10r build` returns `AlreadyCurrent` when the sources and analyzer are unchanged (`current_index_accounting`, `src/commands.rs:658-705`).
  The remedy that works is `c10r build --force`.
- The non-UTF-8 and non-Unicode path warnings (`src/commands.rs:117`, `:130`) are printed by the freshness scan on every query, and they say `excluded from the build` even when no build is running.
- `store error: {0}` (three enums) passes raw rusqlite text through with no context.
- The no-index messages differ in wording across three sites, and none mentions that the default `--db` is relative to the current directory.
  Adding `--db` as a remedy is right for the CLI but wrong for MCP, which never passes `--db` (`mcp/src/c10r_mcp/binary.py` docstring), so the MCP layer needs its own wording.
